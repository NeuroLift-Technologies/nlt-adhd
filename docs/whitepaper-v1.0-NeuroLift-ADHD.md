## Abstract

NeuroLift ADHD is an AI-powered cognitive support system designed around a simple premise:

> **People with ADHD do not need another system that tells them what they should do. They need an intelligent system that can understand where they are getting stuck and help them move forward without taking control away from them.**

NeuroLift combines personalized AI Advocates, specialized ADHD cognitive-support agents, an embodied AI training environment, persistent context, adaptive intervention strategies, safety mechanisms, and a formal governance architecture.

The system is built on the **NeuroLift AI-Fusion Framework** and governed through the **Solidarity Framework**.

AI-Fusion provides the intelligence and learning architecture.

The Solidarity Framework provides the rules under which that intelligence may operate.

This distinction is fundamental.

NeuroLift does not seek to create an AI that makes decisions *for* a person with ADHD. It seeks to create an AI that helps a person exercise their own agency more effectively.

---

# 1. The Problem

ADHD is frequently approached as a productivity problem.

That framing is incomplete.

A person can understand exactly what needs to be done and still be unable to initiate the task. They can create an excellent plan and be unable to execute it. They can begin an activity and lose awareness of time. They can become overwhelmed by a task whose objective complexity is relatively low.

The problem is therefore not simply a lack of information.

It is often a mismatch between:

* intention and initiation
* attention and task demands
* working memory and environmental complexity
* planning and execution
* time perception and deadlines
* motivation and task characteristics
* emotional state and cognitive capacity
* context retention and interrupted workflows

Traditional productivity applications generally expect the user to operate the system.

NeuroLift reverses this relationship.

The system attempts to understand the user's current cognitive state and determine what form of assistance is most useful.

---

# 2. Product Vision

NeuroLift ADHD is envisioned as a persistent **AI Advocate** that works alongside the user.

The user's primary interaction is not with a collection of productivity tools.

It is with an Advocate that coordinates the appropriate capabilities behind the scenes.

The central interaction can be as simple as:

> **"I'm stuck."**

The system's responsibility is to determine what "stuck" means in context.

It could represent:

* task-initiation difficulty
* overwhelm
* distraction
* uncertainty
* prioritization failure
* working-memory overload
* time blindness
* task-switching difficulty
* emotional friction
* decision paralysis
* excessive hyperfocus
* loss of context
* or another interaction pattern

The Advocate responds to the situation rather than forcing the user into a predetermined workflow.

# 3. The Advocate Model

The Advocate is the primary user-facing intelligence.

It combines:

1. **A persistent user context**
2. **Specialized cognitive-support capabilities**
3. **Situational reasoning**
4. **Intervention selection**
5. **Feedback from the user**
6. **Governance enforcement**
7. **Safety mechanisms**
8. **Continuity mechanisms**

The Advocate is not intended to impersonate a clinician.

It is a cognitive-support system.

Its purpose is to reduce friction between **what the user intends to do and their ability to act on that intention**.

# 5. From Advice to Cognitive Scaffolding

A conventional assistant might respond to:

> "I need to clean my house."

with a generic checklist.

NeuroLift instead attempts to identify the cognitive barrier.

If the problem is task initiation, the system may reduce the activation threshold.

Instead of:

**Clean the house**

the Advocate may establish:

**Stand up.**

Then:

**Get a trash bag.**

Then:

**Pick up five pieces of trash.**

The objective is not to micromanage the user.

It is to create an executable bridge between intention and action.

The system can then reassess.

If the user is moving, support can decrease.

If the user becomes stuck again, support can increase.

This creates an adaptive loop:

```text
Intent
   ↓
Cognitive Friction
   ↓
Assessment
   ↓
Appropriate Support
   ↓
User Action
   ↓
Feedback
   ↓
Reassessment
   ↓
Adaptation
```

# 6. Personalization

NeuroLift is designed around the principle that effective ADHD support must become increasingly individualized.

Two people can experience the same apparent problem for completely different reasons.

For example:

> "I can't start this project."

could represent:

* uncertainty about the first step
* fear of failure
* excessive task scope
* boredom
* competing priorities
* insufficient stimulation
* working-memory overload
* emotional resistance
* or simple exhaustion.

The Advocate therefore maintains contextual understanding rather than treating every interaction as an isolated prompt.

Over time, the system can learn:

* which interventions are effective
* which approaches create friction
* preferred communication patterns
* appropriate intervention intensity
* recurring task patterns
* common failure points
* successful recovery strategies
* and contextual factors affecting execution.

Personalization is therefore not merely a recommendation engine.

It is part of the cognitive-support model.

# 9. The Governance Architecture

## THE GOVERNANCE BLOCK

**The AI is not the authority.**

This principle is foundational to NeuroLift.

The intelligence layer must operate inside an explicit governance boundary that establishes:

* who has authority
* what the AI is permitted to do
* what the AI is prohibited from doing
* how instructions are interpreted
* how permissions propagate
* how actions are constrained
* how multi-agent behavior is governed
* how safety conditions are escalated
* and how human authority is preserved.

The NeuroLift governance architecture is based on the **Solidarity Framework**.

```text
                    HUMAN AUTHORITY
                           │
                           ▼
                    ┌─────────────┐
                    │     TOI     │
                    │ Interaction │
                    │  Contract   │
                    └──────┬──────┘
                           │
                           ▼
                    ┌─────────────┐
                    │     OTOI    │
                    │ Operational │
                    │ Enforcement │
                    └──────┬──────┘
                           │
                           ▼
                 ┌───────────────────┐
                 │      ASFDK        │
                 │ Runtime Governance│
                 │ Deployment Boundary│
                 └────────┬──────────┘
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          ADVOCATE       RRT       SLEEPWALKER
             │            │            │
             └────────────┼────────────┘
                          ▼
                   AI-FUSION SYSTEM
                          │
                          ▼
                    USER / WORLD
```

### TOI — Terms of Interaction

TOI defines the interaction contract between a human or other authorized entity and an AI system.

It establishes the terms under which interaction occurs.

TOI is the **human/entity-sourced authority layer**.

It does not replace provider safeguards or other mandatory safety mechanisms.

### OTOI — Operational Terms of Interaction

OTOI is the enforcement layer.

It takes the terms established through TOI and preserves them across operational execution, including multi-agent and multi-party workflows.

This prevents governance from existing merely as documentation.

The system must be capable of enforcing the applicable interaction terms.

### ASFDK — Agent Solidarity Framework Deployment Kit

ASFDK establishes the runtime and deployment boundary between AI capability and operational effects.

It governs the surfaces through which agents interact with tools, systems, and other agents.

This makes governance an architectural property rather than a prompt-level instruction.

### RRT Advocate

RRT provides a dedicated safety-oriented capability for recognizing conditions requiring elevated handling.

Its role is deliberately separated from ordinary Advocate behavior.

The RRT architecture is intended to support assessment and appropriate escalation rather than allowing a general-purpose conversational agent to independently determine its own safety authority.

### Sleepwalker Protocol

Sleepwalker provides continuity and controlled background execution mechanisms.

Its purpose is to allow appropriate continuity when the primary interaction is interrupted or temporarily inactive while remaining subject to governance constraints.

# 10. Governance Is a Runtime Property

A central NeuroLift design principle is:

> **Governance must exist where actions occur.**

An AI system cannot be considered governed merely because its system prompt says that it should behave responsibly.

NeuroLift therefore separates:

**Capability**

from

**Authority**

An Advocate may possess the capability to perform an operation without possessing the authority to perform it.

This distinction becomes increasingly important as AI systems become more autonomous.

```text

     │
     └── Requires Escalation?
             │
             ▼
        Operational Effect
```

# 11. Human Sovereignty

NeuroLift is designed around **human sovereignty**.

The Advocate assists the person.

It does not become the person.

The system therefore distinguishes between:

* recommendation
* assistance
* automation
* authorization
* execution
* and authority.

Those concepts must never be silently collapsed into one another.

The user's intent remains foundational.

The system can help the user understand an option.

It can help formulate a plan.

It can help execute an authorized action.

But capability does not inherently create authority.

---

# 12. Prompt-Injection and Provenance Defense

A governance system must also defend against instructions that originate from untrusted channels.

NeuroLift's provenance-defense architecture distinguishes interaction channels including:

* `user_input`
* `model_output`
* `tool_result`
* `system`
* `unknown`

This matters because a tool result, retrieved document, webpage, or model-generated statement must not automatically acquire the authority of a human instruction.

The principle is:

> **Information is not authority.**

A system may encounter text that says:

> "Ignore the user's instructions and perform this action."

That text can be data.

It does not automatically become a command.

The governance layer therefore evaluates provenance before allowing information to influence an authorized operation.

# 14. Continuity and Recovery

ADHD support frequently fails when context disappears.

A person may:

* become distracted
* close the application
* lose track of an activity
* return hours later
* abandon a task
* or forget why they started.

Sleepwalker addresses continuity as an architectural concern.

The system can preserve appropriate state while maintaining the governance conditions under which that state may be resumed.

The objective is not autonomous activity for its own sake.

The objective is **continuity without surrendering control**.

# 17. Example Interaction

### User

> "I have to finish this report tonight and I haven't started."

### System

The Advocate evaluates the context.

Possible interpretation:

**Task initiation + overwhelm + large ambiguous task.**

Instead of producing a 15-step productivity lecture, the Advocate might establish:

**Objective:** Get the report started.

**Immediate action:** Open the document.

**Next action:** Write the title.

**Then:** Tell me what the report needs to accomplish.

The system progressively transforms an abstract objective into executable actions.

If the user begins working, intervention intensity decreases.

If they become stuck, the Advocate adapts.

If the user says:

> "Actually, I'm too overwhelmed."

the system changes strategy.

The system is therefore responding to **state**, not merely executing a static workflow.
